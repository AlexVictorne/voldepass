# Voldepass

Zero-knowledge менеджер паролей: REST-сервер (Go, chi, PostgreSQL) + CLI/TUI-клиент
с шифрованием на стороне клиента (end-to-end). Сервер никогда не видит открытые
пароли, содержимое записей или ключ шифрования, который их защищает.

## Почему «Voldepass»

Имя — каламбур из «пароль» (password) и знаменитого литературного тёмного волшебника,
которого принято не называть по имени. Параллель с zero-knowledge моделью прямая:
сервер, как и персонажи той истории, никогда не «произносит» и не видит мастер-пароль
и защищённые им секреты — он лишь хранит зашифрованные артефакты, не зная, что за ними
скрывается.

## Архитектура

Гексагональная архитектура (ports & adapters). `internal/domain` содержит сущности,
не зависящие от фреймворков; каждая сторона (`server`, `client`) выстраивает поверх
неё слои config → storage/transport → auth → service → transport/CLI.

```
cmd/
  server/          точка входа: config → app.New → HTTP-сервер + фоновые задачи
  client/          точка входа: корневая cobra-команда (CLI + TUI)
internal/
  domain/          сущности, ошибки, DTO Sync API — без внутренних импортов
  server/
    config/        слоистый конфиг (defaults → JSON → env → флаги)
    storage/
      postgres/    репозитории на pgx/v5 + вкомпилированные golang-migrate миграции
      inmem/       in-memory репозитории (используются в юнит-тестах server/service)
    auth/          JWT, хранилище challenge, ротация refresh-токенов
    service/       AuthService, VaultService, SyncService (бизнес-логика)
    rest/          chi-роутер, хендлеры, middleware
    app/           сборка зависимостей: config → storage → services → router, graceful shutdown
  client/
    config/        слоистый конфиг (клиентская сторона)
    crypto/        Argon2id, AES-256-GCM, HMAC-аутентификация, TOTP, экспорт-бандл, генератор паролей
    transport/     retryablehttp-клиент: двухфазный login, авто-рефреш, TLS pinning
    storage/       in-memory + зашифрованный файл на диске (атомарная запись)
    service/       AuthFlow, VaultManager, Syncer, Session (оркестрация клиента)
    cli/           cobra-команды
    tui/           bubbletea-экраны (логин/список/детали)
test/
  integration/     -tags=integration, реальный PostgreSQL через testcontainers
  e2e/             -tags=e2e, сборка бинарей + smoke-проверки
```

## Криптографическая модель

Мастер-пароль никогда не покидает клиент и никогда не передаётся по сети.

1. **Деривация ключей (Argon2id).** Из `(masterPassword, kdfSalt)` клиент выводит два
   независимых ключа через Argon2id с разделением домена: `authKey` (используется
   только для аутентификации) и `encKey` (используется только для обёртки/разворачивания
   ключа данных).
2. **Обёртка ключа.** Случайный 256-битный `dataKey` шифрует каждую запись хранилища
   (AES-256-GCM, случайный nonce на запись). `dataKey` оборачивается `encKey`
   (`wrappedDataKey = AES-GCM(encKey, dataKey)`) и хранится на сервере как часть
   профиля пользователя — именно это позволяет второму устройству разблокировать
   хранилище после входа, ни разу не передав по сети `dataKey` или сам пароль.
3. **Challenge-response аутентификация.** Вход — это два HTTP-запроса:
   `POST /login/challenge {login}` → сервер возвращает одноразовый `serverNonce`
   (с TTL, гасится при первом использовании) и профиль (`kdfSalt`, `kdfParams`,
   `wrappedDataKey`). Клиент вычисляет `authMsg = HMAC-SHA256(authKey, serverNonce)`
   и отправляет `POST /login {login, authMsg}`. Открытый пароль и `authKey` никогда
   не передаются по сети; перехваченный `authMsg` нельзя переиспользовать, так как
   nonce одноразовый.
4. **Токены сессии.** Успешный вход возвращает короткоживущий JWT access-токен (~15 мин)
   и непрозрачный refresh-токен (~30 дней, ротируется при каждом использовании;
   повторное использование уже ротированного refresh-токена отзывает всю цепочку
   токенов — детект кражи).

## Протокол синхронизации

`GET /api/v1/sync?since=<version>` возвращает все записи, изменённые после `version`.
`POST /api/v1/sync` (заголовок `Idempotency-Key`) отправляет пакет локально изменённых
записей; каждая несёт `base_version` для optimistic locking. Сервер отвечает по каждой
записи `applied` (новая версия) или `conflict` (возвращает текущую серверную запись).

Клиентский `Syncer` (`internal/client/service/syncer.go`) реализует:

- **Pull → merge.** Не-dirty локальные записи продвигаются (fast-forward) до серверной
  версии. Локальная запись, одновременно изменённая и локально, и на сервере, при
  конфликте разрешается по правилам delete-wins (tombstone побеждает безусловно) и
  LWW по времени (`RecordDTO.UpdatedAt` против локального `DirtyAt`) — проигравшая
  сторона сохраняется отдельной **conflict-копией** (новый ID), данные никогда не
  теряются молча.
- **Идемпотентность push.** Ключ идемпотентности для пакета push персистируется в
  локальное хранилище *до* отправки запроса — повтор после краша переиспользует тот же
  ключ, и сервер возвращает закэшированный результат вместо повторного применения.
- **Чанкинг.** Большие пакеты разбиваются на части (настраиваемо, по умолчанию 100
  записей на запрос).
- **Цикл сходимости.** Pull → push повторяется (с ограничением, по умолчанию 5
  итераций), пока не исчезнут конфликты или не будет исчерпан лимит; записи, всё ещё
  остающиеся dirty, возвращаются вызывающему коду для ручного разрешения.

## Сборка

```sh
make build            # оба бинаря в ./bin
make build-server
make build-client
```

Матрица кросс-компиляции (linux/darwin/windows, amd64):

```sh
make build-all-platforms
```

Версия и дата сборки прокидываются через `-ldflags` и печатаются `voldepass-server`
при старте и `voldepass-client version`.

## Запуск сервера

```sh
make up                     # docker compose: PostgreSQL 16
export VOLDEPASS_JWT_SECRET=$(openssl rand -hex 32)
./bin/voldepass-server
```

Конфигурация собирается послойно: `defaults → JSON-файл (-config) → env (VOLDEPASS_*)
→ флаги` — одинаково у клиента и сервера. Полный список полей — в
`internal/server/config/config.go` и `internal/client/config/config.go`.

## Использование CLI

```sh
export VOLDEPASS_LOGIN=alice
./bin/voldepass-client register            # запросит мастер-пароль
./bin/voldepass-client add --type text --content "note" --meta "personal"
./bin/voldepass-client list
./bin/voldepass-client sync
./bin/voldepass-client otp get --id <record-id>
./bin/voldepass-client export --output backup.gkenc
./bin/voldepass-client import --input backup.gkenc
./bin/voldepass-client generate --length 24
./bin/voldepass-client tui                  # интерактивный терминальный интерфейс
```

Каждая команда, затрагивающая хранилище, заново проходит challenge-response
аутентификацию и выводит `dataKey` заново на каждый вызов; между процессами CLI
ничего чувствительного не кэшируется, кроме зашифрованного локального файла.

## Использование TUI

```sh
./bin/voldepass-client tui
```

Интерактивный терминальный интерфейс на [bubbletea](https://github.com/charmbracelet/bubbletea)
(`internal/client/tui`) поверх той же аутентификации и `VaultManager`, что и CLI —
никакой отдельной бизнес-логики, только другой UI поверх одного и того же клиентского ядра.

Экраны:

- **Логин** — `Tab` переключает поля логин/пароль, `Enter` входит, `Esc` выходит из TUI.
- **Список записей** — `↑`/`↓` (или `j`/`k`) навигация, `Enter` открывает запись,
  `n` добавляет новую, `d` удаляет выбранную (с подтверждением `y`/`n`), `s` синхронизирует
  с сервером вручную, внизу экрана всегда видно время последней синхронизации, `q` выходит
  (сохраняя сессию и локальное хранилище).
- **Детали записи** — показывает расшифрованные meta и payload; для OTP-записей код
  TOTP обновляется вживую по таймеру, без повторного открытия экрана. `e` открывает
  редактирование текущей записи, `Esc`/`b` — назад к списку.
- **Добавление / редактирование** — единая динамическая форма, поля зависят от выбранного
  типа записи (Credentials/Text/Binary/Card/OTP); при редактировании форма предзаполняется
  текущими расшифрованными значениями. `Tab`/`Shift+Tab` — между полями, `Enter` на
  последнем поле сохраняет, `Esc` отменяет без изменений.

Как и в CLI, `Create`/`Update`/`Delete` — чисто локальные операции (шифрование +
запись в локальное хранилище); отправка изменений на сервер происходит отдельно,
по `s` или при штатном выходе.

## Тестирование

Пять уровней, от быстрых/дешёвых к медленным/дорогим:

```sh
make lint              # golangci-lint + go vet + govulncheck + go mod verify + check-migrations
make test              # юнит + функциональные, -race, порог покрытия ≥70%
make test-integration  # реальный PostgreSQL через testcontainers (требует Docker)
make test-e2e          # сборка бинарей + smoke-проверки
make test-all          # всё вышеперечисленное
```

Тесты функционального уровня (сервисы, REST-хендлеры, CLI-команды) гоняются против
полнофункциональных in-memory стеков — не моков — так что `AuthService`,
`VaultService`, `SyncService`, chi-роутер и cobra-команды CLI проверяются целиком,
без реальной БД или сети.

## Ограничения zero-knowledge модели

Это осознанные компромиссы дизайна v1, а не недосмотры:

- **Нет восстановления пароля.** Сервер не может восстановить или сбросить
  мастер-пароль. Потеря пароля означает потерю хранилища (серверного эскроу `dataKey`
  по дизайну не существует). `export`/`import`-бандлы — единственный механизм бэкапа.
- **Утечка метаданных.** Сервер не может прочитать содержимое записи, но видит размер
  шифротекста, тип записи и время/частоту изменений — по ним возможен анализ паттернов
  использования. `meta` каждой записи шифруется отдельно, но её наличие и размер
  всё равно видны.
- **Сервер хранит компоненты, нужные для challenge-response и синхронизации между
  устройствами** (верификатор `authKey`, `wrappedDataKey`, `kdfSalt`). Это осознанный
  компромисс (см. заметки исходного дизайна) ради входа со второго устройства без
  какого-либо внеполосного обмена. Утечка БД делает возможным офлайн-перебор
  мастер-пароля; параметры Argon2id — основная защита. Схема без верификатора (SRP),
  полностью устраняющая этот компромисс, — вне рамок v1.
- **Защита от replay, а не от утечки.** Challenge-response не даёт переиспользовать
  перехваченный `authMsg`, но не защищает от офлайн-перебора при компрометации БД.
- **Ключевой материал живёт в памяти процесса на время сессии.** `authKey`/`encKey`/
  `dataKey` хранятся в памяти ровно столько, сколько нужно, и явно обнуляются при
  graceful shutdown (`Session.Close`), но сборщик мусора Go не даёт гарантий об
  отсутствии копий в других местах кучи/стека; защита от dump-атак на память — вне
  рамок проекта.
- **Требуется доверие к клиентскому бинарю.** Модель безопасности работает только пока
  клиентский бинарь не скомпрометирован — целостность цепочки поставки клиента вне
  рамок этого проекта.
